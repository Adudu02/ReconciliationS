# ADR-009 Review decisions and derived read models

Status: accepted. Implements group 8A, design D6/D11/D14/D16 and the group 8 amendments in ADR-007. Task 8.5 is a separate UI delivery (8B).

## Decision resource and transaction boundary

POST `/companies/{companyId}/links/{linkId}/decisions` accepts confirm, reject or change. Accountant and administrator roles may write; viewers may read. Archived companies remain readable and refuse decisions. CompanyScope sets the RLS company context and locks the company for a write. The handler selects the company-scoped link FOR UPDATE, then locks its movement and target invoice before checking capacity. Unknown or foreign resource ids return 404. Decisions on reconciled, rejected or closed links return 409 with the current state; only suggested links are candidates. A user-origin suggestion is protected unless it is a cancellation marker being rejected or changed. Concurrent requests on the same link have exactly one winner.

M0012 adds link_decision: id, company_id, link_id, type, decided_by, decided_at and JSON detail. Forced RLS and composite foreign keys apply. The cfdi_app role has SELECT and INSERT only. Each request inserts one decision and calls ADR-006's append function in the same tenant transaction. Confirm and reject append one audit entry. Change appends two audit entries, closing the old link and creating the new one, while retaining a single decision row. This is the explicit exception to the spec's general one-entry wording because its change scenario requires both actions to be recorded. Typed items identify links, movements and CFDI UUIDs. Note text is limited to 500 characters, retained in decision detail and omitted from audit detail and application logs.

Confirm preserves automatic origin, sets actor/time, and rechecks both confirmed movement capacity and invoice remaining net payable. A cancellation-marked suggestion cannot be confirmed. Reject produces a user rejection tombstone and releases capacity. Change closes the old suggestion and creates a new user-origin reconciled link. The target must be an issued, non-cancelled invoice in the same company; global invoices are allowed manually. Movement capacity is strict. Manual application above remaining invoice payable is allowed and produces the existing overpaid review reason. An unreopened user rejection blocks the target pair. Accepting a replacement closes its obsolete cancellation marker, preserving history.

An optional payment attachment must provide BOTH payment_cfdi_id and payment_ref. The complement must be type P, visible in the company and non-cancelled. The referenced payment must belong to it and contain a document referencing the target invoice UUID. A payment already claimed by a different reconciled movement returns 409. This preserves 6B's first-claim rule: one payment row may cover several invoice allocations of the same winning movement. No amount/date inference creates attachment coverage.

## Active uniqueness and safe downgrade

This amends ADR-007's original unconditional unique-key statement. A change to the same invoice with a different amount must retain the old row and create a new row. M0012 therefore uses a unique index on `(company_id,movement_id,cfdi_id,payment_cfdi_id)` with NULLS NOT DISTINCT WHERE state IN ('suggested','reconciled'). Historical rows may share a pair; active rows may not. User change closures and user rejections block automatic pair re-proposal. Automatic cleanup/supersede history still participates in the engine's existing blocked-pair checks, preventing flapping.

The engine persistence and cancellation replacement insert paths use primary-key ON CONFLICT updates for known upgrade/reopened ids, plus explicit proposal checks; they do not rely on an unconditional pair constraint. Decision creation checks active/rejected pairs under the company lock. No replacement pair-target ON CONFLICT clause is needed for those id-targeted updates.

Down refuses if link_decision contains any user decisions or if historical duplicate pairs prevent restoring the old constraint. It never deletes decision history to make a downgrade fit. Downgrades past M0012 require explicit manual export/cleanup of decisions by an operator, with API/workers stopped. The audit entries and chain head are never touched by Down. Up/down/up on populated data without decisions preserves invoices, movements, links and audit hashes; refusal tests preserve decision rows and the partial index.

## Read model and paging

Review, summaries, lists and overview compute their answer from existing company-scoped SQL functions: cfdi_payable, cfdi_state, movement_state and cfdi_review_reasons. These are set-based reads, with no per-row function calls. No persisted state column is introduced.

The review queue includes suggested links and invoices whose reasons contain requiresReview=true. Informational fully credited and global invoice reasons alone do not create a queue item. Reconciled links are excluded; a reconciled invoice with a problem such as overpaid can still be an invoice flag. Link entries sort high, medium, low, then movement date/id; invoice flags follow, ordered by invoice date/id. All cursor components must be supplied together. Pages default to 50, maximum 200. The keyset cursor is `(afterRank,afterDate,afterId)` and does not provide a transaction snapshot across requests: concurrent decisions can remove entries between pages.

Invoice lists use `(afterIssuedAt,afterId)` and type/direction/state/complement filters. Pending lists require pendingAmount > 0, excluding fully credited invoices. Missing complements include unreceived complements even after their deadline; overdue is the narrower due-date-passed filter. Both return the earliest outstanding due date. Reasons retain their `{code,requiresReview}` shape.

Summaries expose total, credit notes, net payable, confirmed paid/percentage/pending, uncoveredAmount after valid suggestions, direction, payment method, SAT/cancellation/EFOS information and all active links with movement amounts, confidence and explicit payment references. The worked example is 11,600.00 with reconciled 5,800.00 and suggested 5,800.00: 50% paid, pendingAmount 5,800.00, uncoveredAmount zero, both movements and the reconciled link's payment CFDI. Complement status uses the 6B claim rule and fifth-of-next-month deadline, optionally adjusted for weekends. Only confirmed PPD payments create deadlines. Suggested and PUE links without received coverage have missing status without a due date. Cancelled invoices do not create deadlines. Cash form 01 above 2,000.00 adds the exact non-blocking warning; it changes no state.

Overview uses one grouped set-based query per resource. Counts and amounts per derived state add up to imported type I invoices and all movements. Classified movements and zero-payable invoices stay in their derived state; the explanatory totals note distinguishes these totals from filtered pending lists. Invoice amounts are imported gross totals, not net payable; movement amounts are credit plus debit. Payment/credit-note documents are not counted as income invoices. Alerts count overdue complements, cancellation in process, actual EFOS warnings and global invoices. The response includes the demo disclaimer.

Company-leading queue, invoice-list and decision-history indexes supplement the existing invoice/state and payment-claim indexes. RLS can prevent non-leakproof predicates from using indexes: plans must be measured as cfdi_app, relying on company_id and ordinary state btree columns rather than assuming JSON predicates are indexable. The opt-in 20,000/20,000 benchmark records actual endpoint SQL EXPLAIN ANALYZE and local request medians; these are observations, not service objectives.

## API version and alternatives

The built-in ASP.NET Core OpenAPI generator stays at anonymous `/openapi.json`. Release info.version is 1.0.0, also returned in x-api-version. Documentation includes bearer JWT, endpoint summaries/tags, role notes, errors and “results have no fiscal or legal validity”. Existing paths are preserved. A future breaking contract introduces a /v2 prefix, runs alongside the old contract during migration, and removes the old version only after callers migrate.

Persisting stored states would duplicate link and credit-note truth and require every cancellation/decision path to update several records correctly. Derived reads keep one source of truth. Using materialized views could reduce repeated aggregation at larger volumes but require refresh/freshness rules and complicate transactional decision feedback; profile first. Separate confirm/reject/change endpoints would fragment one decision history. Reusing the old row for change would erase its prior target/amount; active uniqueness permits retained history with one clear new link.

## Known gaps

There is no reopen endpoint, no standalone manual N:M creation resource, and no UI in 8A. Task 8.5 remains pending for 8B. FX remains group 6.11; no exchange gains or losses are invented here. UTC determines today, weekend adjustment models no holidays, and the fiscal/demo disclaimer remains mandatory.
